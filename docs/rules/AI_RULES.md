# AI Development Rules & Coding Standards - BANTAWAN

เอกสารนี้กำหนดข้อบังคับเชิงสถาปัตยกรรม มาตรฐานการเขียนโค้ด (Coding Standards) และกฎระเบียบการปฏิบัติตนสำหรับปัญญาประดิษฐ์ (AI Assistant) ทุกตัวที่เข้ามาร่วมแก้ไข ดัดแปลง หรือเขียนซอร์สโค้ดเพิ่มเติมให้กับโปรเจกต์ BANTAWAN เพื่อรักษาเสถียรภาพและคุณภาพสูงสุดของซอฟต์แวร์

---

## 🚨 1. กฎการแก้ไขและควบคุมซอร์สโค้ด (Code Modification Rules)

*   **ห้ามเขียนทับโค้ดทั้งไฟล์ (Strictly No Full-File Overwrite)**:
    *   หลีกเลี่ยงการเขียนโค้ดทับทั้งหน้ากระดาษ ให้ระบุพิกัดแก้ไขเฉพาะขอบเขตบรรทัดที่เป็นเป้าหมายทางตรงเท่านั้น เพื่อลดภาระค่าจราจร (Tokens) และรักษาสัญญาการทำประวัติของไฟล์ (Git History)
*   **แก้ไขแบบระบุเป้าหมายชัดเจน (Targeted Code Modifications)**:
    *   ระบุและลงมือเขียนโค้ดปรับปรุงเฉพาะส่วนที่ได้รับมอบหมายทางตรงจากคำสั่งของผู้ใช้ (User Request) เท่านั้น ห้ามทำการขยายขอบเขตแก้ไขฟังก์ชันข้างเคียงโดยไม่ได้รับอนุมัติล่วงหน้า
*   **รักษาข้อกำหนดคอมเมนต์เดิม (Preserve Existing Comments)**:
    *   ห้ามลบคำอธิบายเชิงลึก (Comments / Docstrings) เก่าที่อ้างอิงอยู่ในฟังก์ชันนั้น ๆ เว้นแต่ว่าฟังก์ชันนั้นจะได้รับการเปลี่ยนตรรกะระบบภายในอย่างถาวร
*   **อธิบายเหตุผลและประเมินผลกระทบ (Explain & Document Changes)**:
    *   ทุกครั้งหลังการปรับปรุงแก้ไขซอร์สโค้ด AI จะต้องระบุอธิบายความคืบหน้า:
        1.  สิ่งที่ทำจริง (รายการที่ปรับเปลี่ยน)
        2.  เหตุผลในการปรับปรุงเชิงเทคนิค
        3.  **ผลกระทบเชิงระบบ (System Impacts)** เช่น การใช้แบตเตอรี่, ผลกระทบต่อ UI หรือ State ของหน้ารอบข้าง
*   **ชี้แจงเมื่อสร้างไฟล์ใหม่ (Justify New File Creation)**:
    *   ห้ามสร้างคลาส บริการ หรือหน้าจอใหม่โดยพร่ำเพรื่อ หากต้องการเพิ่มไฟล์ใหม่ AI จะต้องระบุเหตุผลความจำเป็น เช่น เพื่อประโยชน์การสืบทอดเชิงวัตถุ หรือการแยกขอบเขตการทำงาน (Separation of Concerns) ให้ผู้ใช้พิจารณาก่อนเสมอ

## 🏛️ 2. กฎการออกแบบและสถาปัตยกรรม (Architecture & Best Practices)

*   **รักษาโครงสร้างการทำงานเดิม (Maintain Architecture Integrity)**:
    *   โปรเจกต์อิงรูปแบบ **MVVM-Service Layer** ร่วมกับ **Provider Pattern** อย่างเคร่งครัด
    *   ห้ามเปลี่ยนวิธีการไหลเวียนของสถานะหรือผูก UI ยิงหา Services โดยตรงเด็ดขาด (View -> Provider/ViewModel -> Services เท่านั้น)
*   **การห้ามทำลายวงจรชีวิต Singleton (No Singleton Disposal)**:
    *   ห้ามลงทะเบียน Singleton Services (เช่น `NearbyService`, `EmergencyToolService`, `ConnectivityService`) ด้วยการเรียกคอนสตรัคเตอร์ปกติในกระบวนการทำงานของ `MultiProvider`
    *   **ต้อง** ประยุกต์ใช้คอนสตรัคเตอร์รูปแบบ `.value` เสมอ เพื่อขจัดปัญหาการ Dispose หน่วยความจำและทรัพยากรฮาร์ดแวร์โดยไม่ตั้งใจ
*   **ความปลอดภัยของ BuildContext บนคำสั่งหน่วงเวลา (Async Context Safety)**:
    *   ห้ามเรียกใช้ `BuildContext` หรืออ้างอิง `ScaffoldMessenger.of(context)` ทันทีหลังจากการยิงกระบวนการทำงานแบบ `await` (Async Gaps) โดยไม่มีการป้องกันสิทธิ์
    *   **ต้อง** ทำการเก็บรักษาข้อมูลตัวอ้างอิง ScaffoldMessenger หรือ ViewModels ไว้เป็นตัวถิ่นก่อนรอรับผลลัพธ์ หรือคัดกรองความปลอดภัยด้วยคำสั่ง `if (context.mounted)` ทุกครั้ง

## ⚙️ 3. มาตรฐานการเขียนโค้ดของบริษัท (Corporate Coding Standards)

*   **กฎการตั้งชื่อ (Naming Convention)**:
    *   ชื่อไฟล์ของซอฟต์แวร์ทั้งหมดต้องใช้สัญญะขีดล่างพิมพ์เล็ก (**snake_case**) เท่านั้น
    *   ชื่อคลาสวิดเจ็ตหรือบริการต้องใช้ตัวอักษรพิมพ์ใหญ่คั่นคำ (**UpperCamelCase**)
    *   ชื่อฟังก์ชันและตัวแปรต้องใช้ตัวพิมพ์เล็กคั่นพิมพ์ใหญ่ (**lowerCamelCase**)
    *   ตัวแปรหรือฟังก์ชันส่วนบุคคลภายในคลาสต้องขึ้นต้นด้วยเครื่องหมายขีดล่าง `_`
*   **ความคลีนและสเปกการวิเคราะห์ (Analysis Warning Zero Policy)**:
    *   โค้ดที่ผ่านการแก้ไขโดย AI จะต้องไม่มีคำแจ้งเตือนคำเตือน Linter หรือ Deprecations ค้างอยู่ในการรันวิเคราะห์ระบบเลย (Zero Warnings Compilation)
    *   หลังทำภารกิจเสร็จสิ้น AI จะต้องกระตุ้นคำสั่งรันทดสอบ `flutter analyze` เสมอเพื่อยืนยันคุณภาพ
*   **การใช้งาน API และฟังก์ชันที่ล้าสมัย (Deprecated APIs)**:
    *   ห้ามเรียกใช้งานคำสั่งที่ล้าสมัยในชุด SDK ปัจจุบัน เช่น ห้ามใช้ `.withOpacity(...)` ให้เปลี่ยนไปใช้ `.withValues(alpha: ...)` แทนเพื่อรักษาคุณภาพสี และห้ามปล่อย `backgroundColor` ค้างไว้ใน `TileLayer`
